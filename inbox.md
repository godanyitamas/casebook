# Inbox

- [x] Retrospective: streaming parser rework — promoted to [case draft](cases/streaming-file-parser-rework.md).
- [x] Concept candidate: explicit progress state / unit of work. Correctness comes from making each unit of work, its identity and its completion explicit, recorded state, instead of relying on timing or on outputs appearing. Cases: progress tables + completion barrier (productionizing), per-date completion ledger (repartitioning), orphan retry state (late-arriving data), batch identity (`query_id`, `batch_id`) instead of a hand-written name + date `txnAppId` (observability). Promoted to [concept draft](concepts/explicit-units-of-work.md).
- [x] Concept candidate: physical layout follows the readers. Layout and access pattern form a contract: the layout is designed for the dominant readers (you can't please everyone equally), and every other reader, including new processes and ad hoc queries, has to take the layout into account to get the performance. Cases: business partition columns for the largest tables (productionizing); a functional column added next to `ingestion_date` (repartitioning); a downstream Gold job that did not benefit from that table's good partitions until it pruned explicitly (append-only CDC, reading the repartitioned table); liquid clustering instead of identity partitions (observability). Promoted to [concept draft](concepts/layout-follows-readers.md).
- [x] Terminology: "partition" means two things in this casebook. A table partition is a directory in the layout (`ingestion_date`, business columns); a Spark partition is one task's input. They meet only through file sizes: Spark sorts and packs the files of all selected table partitions together, so one task can read files from several dates, and a large splittable file can span several tasks (`DataSourceScanExec`, `FilePartition`; `labs/spark-job-anatomy/`). Candidate one-line note for `concepts/layout-follows-readers.md`. Added there (repo review, 2026-11-23).
